# feetech-servo v0.7.1 + condition-tolerant servo reads

**Date:** 2026-09-04
**Branch:** `feetech-0.7-condition-reads` (from `main` @ 7a33fae)
**Status:** approved design, pre-implementation

## Problem

`internal/controller` discards a valid servo reading whenever the servo sets any status
flag. An overloaded servo (a gripper clamped on a part, a hot joint) is therefore
unreadable: every read path returns an error and no data. There are seven —
`ServoPositionPercent`, `AnyServoMoving`, `SyncReadPositions`,
`GetJointPositionsAndMovingForServos` (the dwell's `readArmState`), `GetJointPositions`,
`GetJointPositionsForServos` (via `group.Positions`) and `LoadForServos` (per-servo
`servo.Load`, the read most likely to meet an overload flag) — and the arm's
`dwellUntilNear`, `WaitForServosToStop`, `IsMoving`, `JointPositions`, and the gripper's
position reads all inherit the blindness.

`feetech-servo` v0.7.0 fixed the library half: reads return the decoded value *and* an
error carrying the condition flags, and `feetech.ConditionStatus(err) (StatusError, bool)`
reports whether the payload alongside an error is usable (true for condition flags,
false for transport failures and request-rejection flags). Open PR #42 adopts this in
`internal/controller` but is stacked on two gripper PRs (#40, #39) that will take longer
to land. This workstream lands only the dependency bump and the read-path adoption on
`main`, so #42 shrinks to the gripper latch.

     `func tolerateCondition(err error) (feetech.StatusError, error)` →

## Why v0.7.1 and not v0.7.0

v0.7.1 adds no API; it changes **writes**: `Bus.WriteRegister`, `RegWrite`, and the
sync-write path return `nil` on condition-only flags (previously an error), and
`Servo.SetID` updates its cached id when only the EEPROM re-lock failed. Every write site
on `main` (`calibrated_servo.go`, `manager.go`, calibration torque-enable) treats a write
error as fatal, and none infers "overloaded" from one, so this is strictly fewer spurious
failures. `Servo.Ping` tolerating flags (v0.7.0) also stops a clamped gripper from failing
arm init and discovery for free. #42 was written against v0.7.0; #42 will pick up v0.7.1
when it rebases.

## Method

`git cherry-pick` is not viable: #42's commits touch `wait_motion.go` (absent on main),
`gripper.go` (diverged), and `ServoLoad` (absent). One hand-written commit, using
`git show 460bba9` and `4012f36` on `origin/gripper-grasp-latch` as the reference for
each hunk. TDD per hunk: inject a status flag through `FakeTransport.SetStatus`, assert
the read returns data + flags, then make it pass.

## CLAUDE.md gotcha to add

> **A servo condition flag is data, not a failed read.** `ServoPositionPercent` and
> `AnyServoMoving` keep the reading when `feetech.ConditionStatus(err)` says the payload
> is usable (overload/overheat/voltage), and return the flags alongside it; only transport
> failures and request-rejection flags still error. `servocmd` carries the flags in a
> `condition` response field rather than an error because a typed error does not survive
> the DoCommand boundary to a remote arm, and as text because a protobuf `Struct` mangles
> numbers. Every position, moving and load read path in the controller routes the decision
> through `tolerateCondition`; a new read path must too. Since feetech-servo v0.7.1 *writes* also return nil on
> condition-only flags, nothing on main can infer "overloaded" from a write failure.

## Risks

- `condition` has no production consumer on `main` until #42 lands; it is the wire
  contract #42 rebases onto. Acceptable, small.
- The structural `ServoOps` interface makes a missed `AnyServoMoving`/
  `ServoPositionPercent` call site a compile error, not a silent one. The five read paths
  whose signatures do not change are the silent risk: a forgotten `tolerateCondition` there
  compiles fine, which is what the per-path test cases are for.
- This goes further than #42 (seven paths, not two). #42's rebase will conflict in
  `manager.go` at the two sites it also touched; resolving toward this branch is correct.
